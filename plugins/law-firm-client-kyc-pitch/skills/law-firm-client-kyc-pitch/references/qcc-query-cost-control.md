## 1. 适用范围与硬规则

本方法适用于企查查及其他按次、按积分或按数据量计费的工商、股权、融资、知识产权、司法和监管数据库。

必须遵守：

- 先读取用户附件、既有报告、本任务此前的工具结果和历史查询台账，再决定是否调用；
- 按“主体 × 数据域”集中采集，不得按报告章节分别采集；
- 同一业务覆盖键已有完整结果时不得换函数或来源重复查询；同一精确调用键在同一任务内最多成功查询一次；
- 一次查询结果供所有相关章节、表格和分析共同复用；
- 成功返回空结果也是有效结果，不得为了“再确认一次”重复调用；
- 不得用另一项高度重合的企查查查询重复验证；关键事实应转向官方公示、法定披露或公司材料核验；
- 调用次数不是研究质量指标。只查询对报告结论确有必要的数据。

## 2. 调用前计划

首个计费调用前完成：

1. 锁定法定主体名称、统一社会信用代码或平台稳定ID，合并历史名称和别名；
2. 将所需信息归入基本工商、股东股权、工商变更、董监高、对外投资、融资、资质许可、IP、司法案件、执行、处罚等数据域；
3. 标明每个数据域会被哪些章节使用；
4. 检查已有结果是否在主体、字段、时点和范围上足以覆盖；
5. 仅为尚未覆盖的唯一查询建立计划项；
6. 工具显示单次积分或费用时汇总预计成本；工具不显示时只列预计唯一调用次数，不猜测价格。

集团知识产权基础扫描应按 [集团范围知识产权调查方法](group-ip-investigation.md) 覆盖全部当前控股或并表主体，但全量目标不构成无上限付费授权。若需要对非核心集团主体逐家付费、多层股权穿透、批量司法/IP分页或其他明显增加计费次数的范围，先向用户说明主体数、数据域、扩展目的和预计唯一调用数量，取得同意后执行。未获同意或工具额度不足时，保留逐主体未完成记录，不得把部分扫描写成全集团完整覆盖。

## 3. 共享查询台账与两级去重键

在当前任务的内部研究底稿中维护两个相互关联的表：

1. **业务覆盖索引：** 每个“主体 × 数据域 × 时点/范围”一行，记录 `coverage_key`、覆盖字段、缺失字段、状态、来源调用ID和使用章节；
2. **实际调用记录：** 每个真实工具调用一行，记录 `call_key`、数据源、工具/函数、规范化参数、页码/游标、结果引用、积分/费用和重试/重查理由。

两个键分别为：

| 键 | 组成 |
|---|---|
| 业务覆盖键 `coverage_key` | 稳定主体ID + 数据域 + 基准日/时间范围 + 规范化需求范围 |
| 精确调用键 `call_key` | 数据源 + 工具/函数/端点 + 稳定主体ID + 规范化参数 + 基准日/时间范围 + 页码/游标 |

`coverage_key` 用于判断“业务信息是否已经足够”，即使拟改用另一个企查查函数或另一数据源，也必须先检查它。`call_key` 用于拦截完全相同的工具调用。章节名称只能记入“使用章节”，不得进入任何键，否则同一股东信息会因第四章和第五章而被误判为两个需求。

企业主体优先使用统一社会信用代码；境外主体使用注册地和注册号；尚未取得代码时暂用法定名称和注册地，识别后立即合并历史名称、简称和别名。自然人优先使用平台稳定人员ID；没有ID时使用姓名、关联企业和角色组合。

数据域使用稳定枚举：`basic_identity`、`group_scope`、`shareholders_current`、`shareholding_history`、`key_personnel`、`outbound_investments`、`qualifications`、`financing_events`、`judicial_cases`、`administrative_penalties`、`ip_patents`、`ip_trademarks`、`ip_software_copyrights`、`ip_domains_other`、`ip_encumbrances_disputes`。较宽范围的既有结果已覆盖较窄需求时，直接复用，不得再发起窄查询。集团IP扫描以“稳定主体ID × IP数据域 × 基准日 × 规范化名称集合”建立覆盖记录；历史名称属于同一主体的查询范围，不得误建成新的主体需求。

综合接口一次覆盖多个数据域时，只建立一条实际调用记录，同时在业务覆盖索引中为各数据域分别建立记录并共同引用该调用ID。不得为了表示多域覆盖而把同一个 `call_key` 计为多次调用。

调用前先使用 [企查查查询台账模板](../templates/qcc_query_ledger.md) 将覆盖需求和唯一调用分别登记为 `in_progress`。其他章节或并行研究者看到相同 `coverage_key` 或 `call_key` 处于 `in_progress` 时必须等待和复用，不得并发调用。

## 4. 调用判定

每次计费调用前依次判断：

1. 相同或更宽 `coverage_key` 已有完整 `success`：直接复用，不再比较工具名称；
2. 相同 `coverage_key` 已有完整 `success_empty`：复用“该范围未返回记录”的结果，不重查；
3. 相同 `coverage_key` 或 `call_key` 为 `in_progress`：等待该结果，不并发调用；
4. 相同 `call_key` 已执行：不得再次调用；
5. 台账仅为 `incomplete`：只补取缺失页、缺失字段或确有必要的不同端点，并记录 `missing_fields`；
6. 台账为 `quota_exhausted`：不得重试原企查查查询，按第8节改用一个适配的备用源；
7. 台账为 `error`：仅在错误明确属于暂时性故障时允许一次重试；
8. 两级键均不存在可覆盖结果：登记计划项后调用一次。

调用完成后，先更新状态、完整性和结果引用，再开始分析或起草。不得因忘记、上下文切换或章节切换而重新调用。

## 5. 允许重查的情形

仅以下情形允许重查，并必须在调用前记录理由：

- 统一社会信用代码或稳定ID不同，确属另一主体；
- 新需求属于既有结果未覆盖的不同数据域或必要字段；
- 原结果明确截断，需获取尚未查询的页码或游标；
- 原快照早于报告基准日，且存在融资、工商变更、处罚、诉讼等可核验的新变化信号；
- 两个可靠来源存在实质冲突，且官方或免费来源无法解决；
- 用户明确要求刷新至新的基准日；
- 原调用明确报错或返回不完整，且尚未使用一次重试机会。

以下不是重查理由：

- 另一章节也需要相同股东、董监高、融资或处罚信息；
- 希望换一种措辞、增加一个表格或补充引用；
- 公司简称、历史名称或关键词写法不同，但稳定主体ID相同；
- 已成功返回空结果；
- 仅为了用同一商业数据库再次“交叉验证”；
- 起草者没有查看已有底稿或工具结果；
- 换用另一个能够返回相同已覆盖字段的企查查函数或端点。

## 6. 常见数据域的跨章节复用

| 一次采集的数据域 | 主要复用章节 |
|---|---|
| 基本工商、历史名称、注册资本 | 第一章、第四章、第五章 |
| 当前股东、历史股权变更、实控关系 | 第一章、第四章、第五章、第七章 |
| 董事、监事、高管及对外任职 | 第四章、第七章、第八章 |
| 对外投资、分支机构、核心子公司 | 第二章、第三章、第四章、第八章 |
| 控股/并表主体全集、控制路径和范围状态 | 第二章、第三章、第四章、第八章 |
| 融资事件及投资方 | 第一章、第四章、第五章 |
| 资质、许可、备案线索 | 第三章、第八章；关键结论转向官方渠道核验 |
| 各集团主体的专利、商标、软著、域名及权利负担/争议 | 第二章、第三章、第六章、第八章 |
| 诉讼、执行、失信及行政处罚 | 第三章、第四章、第七章、第八章 |

章节需要新增分析时，回到已经取得的结构化结果，不得回到计费工具重复取数。

## 7. 空结果、报错、分页与批量查询

- **空结果：** 工具成功但无记录时记为 `success_empty`，保存查询主体、参数和时间；不得原样或用同义参数重试。
- **报错：** 先区分工具错误与业务空结果。暂时性错误最多重试一次；参数错误应先修正去重键和参数，再调用一次。
- **积分不足：** 企查查明确返回积分、额度或配额不足时记为 `quota_exhausted`，不得归入 `success_empty` 或声称公司无记录，也不得重试企查查消耗同类积分。
- **分页：** 页码或游标属于去重键。一般数据只获取支撑报告所需的页；集团IP基础扫描若以“完整覆盖”交付，则必须取得能够证明结果完整的全部必要页，或把截断数据域记为 `incomplete`，不得在未完成分页时声称全量覆盖。
- **批量：** 仅在已知批量接口可减少计费单位或避免重复时使用。若计费规则未知，以减少唯一计费数据单元为目标，不把“请求数少”误当成“积分少”。
- **重叠端点：** 优先选择能够一次覆盖必要字段的端点。已有宽结果时不得再调用高度重合的窄端点。

## 8. 企查查积分不足时的备用路由

企查查返回 `quota_exhausted` 后，对基础工商或公司信息执行：

1. 先检查台账、用户附件和本任务已有结果，已有足够字段时不再调用；
2. 识别当前可调用的元典MCP、iFind MCP及Wind MCP分别能够返回哪些字段；
3. 一般企业选择当前能够提供法定名称、统一社会信用代码、成立日期、法定代表人、注册资本、登记状态、注册地址或经营范围等所需字段的一个备用源；
4. 上市、挂牌或发债主体可优先选择iFind或Wind中覆盖更完整的一项，并结合交易所或法定披露核验；
5. 任一备用源已覆盖本次必要字段后立即停止，不得为了“多源确认”继续把元典、iFind和Wind全部调用一遍；
6. 第一备用源仅返回部分字段时，先记录已覆盖字段，再只针对缺失字段选择第二备用源；不得重新获取整套基础信息；
7. 将备用源名称、查询时间、覆盖字段和结果引用写入台账。不同数据源使用各自的 `call_key`，同时在同一 `coverage_key` 下标明已满足或仍缺失；
8. 所有可用备用源均不能覆盖时，写明“企查查额度不足且当前备用源未覆盖该字段”，不得写成“未查询到该公司”或“无相关记录”。

元典、iFind和Wind是按当前可用能力选择的备用来源，不是每次都必须依次调用的固定链条。若这些工具本身也按次或按积分计费，同样执行本文件的去重和成本控制规则。

## 9. 更新任务与并行研究

更新既有报告时，先载入旧台账并比较新旧报告基准日。只刷新有变化信号、已过时或用户明确指定的数据域。例如仅更新融资历史时，不得自动重查董监高、司法案件或资质；融资已导致股东变化时，才新增一次股东快照查询。

多代理或多模块并行时，指定一个数据采集者负责所有计费型调用，或使用同一共享台账和 `in_progress` 占位。章节起草者只能消费底稿；不得各自调用企查查。`draft`、`check` 和 `export` 阶段计费调用数必须为零；发现缺口时返回 `research` 执行去重闸门。

## 10. 完成与交付记录

任务完成时，在交付说明中简要报告：

- 唯一计费调用次数；
- 复用命中次数或避免的重复调用数；
- 重试及其理由；
- 因企查查额度不足改用的备用数据源及其覆盖字段；
- 集团IP调查的当前范围主体总数、已扫描数、部分/未覆盖数及其原因；
- 工具明确返回的积分或费用（如有）。

上述信息属于交付说明或内部底稿，不得作为第九章写入固定八章报告。无法可靠统计时如实说明，不得虚构。

验收时应确认：相同成功或成功空结果的 `call_key` 不超过一次；重复 `coverage_key` 仅在允许重查且已记录理由时存在；技术重试不超过一次。
